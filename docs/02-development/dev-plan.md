## 작업 규칙 (반드시 지킨다)

1. **단계 착수 전 고객 승인을 받는다.** 어떤 작업을 할지 제시하고, 승인 이후에만 코드를 쓴다.
2. **대화 중 작업 내용이 바뀌면 이 문서를 먼저 고치고** 다시 승인을 기다린다. 문서와 다른 것을 만들지 않는다.
3. 단계를 마치면 **진행 로그**를 갱신하고 그날의 [작업 일지](../03-worklog/)를 남긴다.
4. 각 단계는 **고객이 눈으로 확인할 수 있는 산출물**로 끝난다. "코드를 썼습니다"로 끝나는 단계를 만들지 않는다.
5. 새로 등장한 기술 개념은 Vault의 `00 Inbox/Raw Import/Personal Study/`에 설명 노트를 남긴다.

## P1. 콘텐츠 파이프라인 PoC

**목적** — Obsidian 마크다운이 실제로 온전히 JSON으로 변환되는지 확인한다. 이 프로젝트 전체에서 **기술적 불확실성이 가장 큰 구간**이므로 먼저 친다.

**작업**
1. `pipeline/` 에 Quartz v4 설치, Vault 사본을 입력으로 연결
2. 화이트리스트 필터 + 제외 규칙 구현 (D-01, D-06)
   - **`03 Company/` 하위는 옵트인 처리** — `publish: true`가 있는 노트만 통과 (D-08)
3. 커스텀 emitter 작성 → `content/*.json`, `graph.json` 출력
4. 난제 검증 — 다음이 전부 되는지 실제 노트로 확인한다
   - 짧은 위키링크(`[[React]]`)와 전체 경로 위키링크 둘 다 해석
   - 한글·공백·`&` 포함 파일명의 슬러그 생성
   - 수식 `$...$` / `$$...$$`, 표, 코드블록
   - frontmatter 없는 노트에서 제목·분류 추출
   - 깨진 링크(존재하지 않는 노트를 가리키는 위키링크) 집계
5. **메타데이터 추출** (D-09) — 본문 첫 문단에서 `description` 생성, 소제목 구조 보존, `slug-map.json` 출력
6. 그래프 초기 좌표 사전 계산
7. 콘텐츠 가드 골격 + `guard-rules.txt` 초안 — 공개 대상 전수 스캔 포함
8. **회사 케이스 1차 판정 초안** (D-08) — 전체 목록에 ✅/🔄/⛔ 판정과 사유를 붙여 [검수 문서](../04-communication/company-case-review.md)에 기록. 파싱이 어차피 도는 단계라 추가 비용이 거의 없고, 공개 가능한 회사 케이스 규모를 일찍 알아야 P5 포트폴리오 구성을 짤 수 있다

**산출물**
- 변환 통계 리포트 — 노트 수, 링크 수, 깨진 링크 목록, 변환 실패 목록
- 대표 노트 5개의 JSON 및 **브라우저로 열어 확인하는 HTML 미리보기**
- `description` 자동 추출 결과 샘플 — 검색 결과에 그대로 뜨는 문장이므로 품질 확인 필요
- 회사 케이스 1차 판정 초안 — 노트별 ✅/🔄/⛔ 및 사유

**고객 확인 사항** — 변환 결과가 Obsidian에서 보던 것과 같은가. 깨진 링크를 어떻게 처리할 것인가(숨김 / 비활성 표시 / 그대로 노출). 자동 추출된 요약문이 검색 결과에 노출해도 될 품질인가. **회사 케이스 1차 판정 초안 중 계약·비밀유지서약 관련 항목** — 이건 본인만 판단 가능하다.

**예상 리스크** — Quartz가 frontmatter 없는 노트나 한글 파일명에서 예상과 다르게 동작할 수 있다. 이 경우 emitter 앞단에 전처리 단계를 넣는다.

## P2. 동기화·배포 파이프라인

**목적** — 빈 페이지라도 좋으니 `hskim.me`가 실제로 뜨고, Vault 커밋이 배포까지 이어지는 경로를 끝까지 뚫는다.

**작업**
1. private 저장소 `hskim-vault` 생성, Vault를 git 저장소로 초기화. **허용 목록 방식** `.gitignore` 로 `01`·`02`·`03` 만 포함
2. Obsidian Git 플러그인 설치·설정 (푸시 주기는 고객과 확정 — 열린 항목 #6)
3. private 저장소 `hskim-me` 생성, 현재 작업물 이전
4. deploy key 발급, `hskim-vault` push → `hskim-me` 빌드 트리거 워크플로 작성
5. Cloudflare Pages 연결, 프리뷰 URL 확보
6. 도메인 `hskim.me` DNS 연결, HTTPS 확인
7. Cloudflare Access로 프리뷰 잠금 (작업 기간 중 비공개 유지)

**산출물** — Vault 커밋 → 사이트 반영 확인 완료 (2026-09-20). `https://www.hskim.me`

**고객 확인 사항** — 도메인 등록기관과 네임서버 현황. Obsidian Git 푸시 주기. GitHub 계정.

**설정 절차** — [infra/README.md](../../infra/README.md)에 6단계로 정리했다. 계정 권한이 필요한 작업이라 고객이 직접 수행하고, 제작자는 결과에 맞춰 설정값만 채운다.

**주의** — 이 단계는 고객 계정 권한이 필요한 작업(도메인 DNS 변경, 저장소 생성)을 포함한다. 해당 작업은 **고객이 직접 수행하거나 명시적 승인 후** 진행한다.

## P3. 노트 렌더링과 탐색

**목적** — 사이트가 "읽을 수 있는 상태"가 된다. 요구사항 5·6번의 본체.

**작업**
1. `web/` Next.js 프로젝트 셋업 (App Router, 정적 export, Tailwind)
2. 노트 페이지 `/notes/[...slug]`, 프로젝트 페이지 `/projects/[...slug]`
3. 마크다운 표현 충실도 — 코드 하이라이트(Shiki), 수식(KaTeX), **다이어그램(Mermaid)**, 표 반응형, 콜아웃
   - JSON의 `features` 플래그로 필요한 문서에서만 KaTeX·Mermaid 로드
   - 다이어그램 **확대·축소·이동·전체화면** (P1 미리보기 구현분 이식. 외부 라이브러리 없이 `viewBox` 조작 + Pointer Events)
4. 위키링크 렌더링 + 호버 미리보기 팝오버
5. 사이드 폴더 트리 (Vault 구조 그대로)
6. 목차(TOC), 백링크 패널
   - **이미지 첨부 처리** — `05 Attachments` 경로 변환·최적화 (첨부가 추가되는 시점에 필요)
7. `/index-all` 텍스트 인덱스 — D-07 대체 경로이자 **크롤러 진입점**(D-09)
8. **페이지 메타데이터 주입** (D-09) — title, description, canonical, OG, JSON-LD(`TechArticle`), `lang="ko"`
9. `sitemap.xml`, `robots.txt` 생성, `slug-map.json` 기반 301 리다이렉트
10. 다크/라이트 테마

**산출물** — 모든 공개 노트를 웹에서 열람 가능. Obsidian 화면과 나란히 비교

**고객 확인 사항** — 원본과 다르게 보이는 부분이 있는지. 타이포그래피·여백.

## P4. 3D 뉴런 그래프 메인

**목적** — 요구사항 4번. 이 사이트의 정체성.

**작업**
1. `react-force-graph-3d`로 기능 검증 — 550개 노드 로드, 클릭 → 노트 이동
2. **여기서 고객 중간 확인** — 기본 3D 그래프 동작을 보고 비주얼 방향 합의
3. **성운 배경 셰이더** (D-10) — GLSL FBM 노이즈, 별먼지 파티클, 시차 효과
4. 뉴런 비주얼 구현 — 발광 노드, 시냅스 엣지, 신호 입자, bloom
5. 인터랙션 — 호버 강조, 1-hop 이웃 부각, 클릭 시 카메라 접근 후 페이지 전환
6. 오버레이 UI (이름, 소개, 진입 버튼)
7. 노트 페이지의 미니 그래프
8. 폴백 — 모바일/저사양/reduced-motion/WebGL 미지원 대응
9. 성능 튜닝 — 인스턴싱, LOD, 프레임률 측정

**산출물** — 메인 화면 동작본. 데스크톱 60fps, 모바일 대체 경로 동작

**고객 확인 사항** — 성운 색감·밀도, 색상 그룹, 회전 속도, 신호 빈도, 전환 연출. 절제 원칙(기획 §7)을 넘지 않았는지

**예상 리스크** — 비주얼 요구를 `react-force-graph-3d`로 못 채우면 R3F 직접 구현으로 전환한다. 이 판단은 3단계 진입 전에 내린다.
