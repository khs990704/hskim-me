## D-02. Quartz의 역할 — 콘텐츠 API 생성기

**결정** — Quartz를 웹사이트 생성기가 아니라 **마크다운 → 구조화 JSON 변환기**로 쓴다. Quartz의 파서·위키링크 해석·백링크/그래프 데이터 생성만 활용하고, 커스텀 emitter로 `content/*.json`, `graph.json`, `search-index.json`을 출력한다. 화면은 전부 별도 프론트엔드에서 그린다.

**근거** — 구상한 3D 뉴런 그래프와 디자인은 Quartz의 Preact 컴포넌트 구조 안에서 만들기 어렵다. 반대로 Obsidian 문법(위키링크, 별칭, 임베드, 콜아웃, 수식)을 직접 다시 구현하는 건 비용이 크다. 둘을 분리하면 파싱은 검증된 구현을 쓰고 표현은 100% 자유로워진다. Quartz 업스트림 업데이트도 파이프라인 계층에서만 흡수하면 된다.

**대안과 기각 사유**
- Quartz 포크 후 컴포넌트 교체 → 초기 속도는 빠르나 3D 그래프·페이지 전환 연출에서 Quartz 빌드 구조에 계속 부딪힌다.
- 자체 remark/rehype 파이프라인 → 의존성은 가볍지만 Obsidian 문법 재현 비용이 초기에 몰린다. 추후 Quartz 의존이 문제가 되면 이 방향으로 이전 가능하도록, 파이프라인 출력 JSON 스키마를 Quartz와 무관하게 정의해 둔다.

**결정일** — 2026-09-20

## D-07. 메인 화면 — 3D 뉴런 그래프 전면

**결정** — 첫 화면은 3D 뉴런 그래프가 전체를 차지한다. 그 위에 최소한의 오버레이(이름 / 한 줄 소개 / 소개·포트폴리오·지식베이스 진입 / 검색)만 얹는다. 채용 담당자용 정리된 이력은 별도 PDF로 제공하므로, 웹은 탐색 경험 자체를 목적으로 삼는다.

**근거** — 고객이 채용 담당자 대상 전달물은 PDF로 분리한다고 확인했다. 따라서 웹이 "읽기 쉬운 이력서" 역할을 겸할 필요가 없고, 정보 전달을 위해 그래프를 희생할 이유가 사라진다.

**보조 결정 (설계자 판단)** — 그래프를 전면에 두되 다음 세 가지는 반드시 함께 만든다. 이게 없으면 "멋있지만 아무것도 찾을 수 없는 사이트"가 된다.
1. **텍스트 대체 경로** — 모바일, 저사양 기기, `prefers-reduced-motion`, 크롤러에는 동일 정보를 담은 정적 인덱스 화면을 제공한다.
2. **항상 열려 있는 탐색 수단** — 사이드 폴더 트리와 검색은 그래프 위에서도 항상 접근 가능해야 한다.
3. **모든 노트 페이지는 정적 HTML** — 그래프는 입구일 뿐, 검색 엔진과 링크 공유는 노트 페이지가 담당한다.

## D-08. 회사 프로젝트 케이스는 옵트인 공개 (D-01 일부 대체)

**결정** — `02 Project Cases/Project Index/03 Company/` 하위는 **기본 비공개**로 전환한다. 노트 frontmatter에 `publish: true`가 명시된 것만 공개한다. 다른 폴더는 D-06의 폴더 기반 자동 공개를 그대로 유지한다.

**경위** — 고객이 "제안한 수준이 충분히 안전하다면 그렇게 해 달라"고 판단을 위임했고, 제작자가 검토한 결과 **자동 패턴 검사만으로는 충분하지 않다**고 판단해 규칙을 강화했다.

**근거**
1. 콘텐츠 가드가 잡는 것은 내부 도메인, 사설 IP, 사번·계정 형식, 고객사 고유명사처럼 **기계적으로 식별되는 것**뿐이다.
2. NDA·영업비밀에서 실제 쟁점이 되는 것은 대개 "그 회사가 이 문제를 어떻게 풀었는가"라는 **설계 판단 자체**다. 고유명사를 전부 지워도 내용만으로 식별되며, 정규식은 이를 판단할 수 없다.
3. 더 중요한 것은 미래다. 자동 공개로 두면 **앞으로 회사 업무를 지식화할 때마다 커밋 즉시 공개**된다. 실제 사고는 이미 있는 문서가 아니라 이 경로에서 난다.
4. 회사 케이스는 수가 한정적이고 한 번만 검토하면 되므로, 여기만 옵트인으로 돌려도 운영 부담이 거의 없다.

**함께 유지되는 것** — 콘텐츠 가드(계층 2), 검수 체크리스트(계층 3), 비공개 프리뷰(계층 4). 기획 문서 §10 참조.

**보조 방침** — 공개가 어려운 케이스는 삭제하지 않고, 구현 세부를 걷어낸 **일반화 버전**을 별도로 작성해 공개하는 선택지를 우선 검토한다. 대부분의 경우 포트폴리오 가치는 거의 그대로 유지된다.

**확정** — 2026-09-20 고객이 판단을 제작자에게 위임함("첫 회사라 누출 없이 공개하는 방법을 잘 모른다"). D-08을 확정안으로 채택한다.

**역할 분담** — 제작자가 판정 초안과 일반화 재작성안을 만들고, 고객은 계약·비밀유지서약 관련 판단(체크리스트 5번)과 최종 공개 승인만 한다. 1차 판정은 P1으로 앞당긴다. 기준·공식·절차는 [company-case-review.md](../04-communication/company-case-review.md).

**원칙 하나** — 원본 노트는 수정하지 않는다. 공개용은 별도 노트로 분리해, Vault 원본의 상세함과 공개본의 안전성을 동시에 유지한다.

## D-09. 검색 엔진 노출을 설계 제약으로 취급

**결정** — 외부 검색 엔진에서 노트의 키워드로 검색했을 때 해당 노트 페이지가 노출되는 것을 요구사항으로 추가한다. 마감 단계의 최적화가 아니라 **P1·P3부터 반영되는 설계 제약**으로 다룬다.

**경위** — 고객이 "외부에서 내 마크다운의 키워드를 검색하면 웹에 노출됐으면 좋겠다"고 추가 요청.

**근거 및 영향**
- 메인이 3D 그래프라 홈 HTML에 크롤러가 읽을 본문이 없다. 색인 경로를 별도로 확보해야 한다 → `/index-all` 텍스트 인덱스를 크롤러 진입점으로 삼고, `sitemap.xml`에 전 URL을 싣는다.
- 노트에 frontmatter가 없으므로 `description`·요약을 **본문 첫 문단에서 파이프라인이 자동 추출**해야 한다. 이는 P1 스키마에 필드를 추가해야 한다는 뜻이다.
- **URL 안정성이 자산이 된다.** 색인이 쌓인 URL이 404가 되면 그동안의 노출이 사라진다. `slug-map.json` 기반 301 리다이렉트는 선택이 아니라 필수가 된다.
- 한글 슬러그를 로마자로 바꾸지 않는다. 검색 엔진은 퍼센트 인코딩된 한글 URL을 디코딩해 처리하며, 한글 키워드가 URL에 있는 편이 매칭에 유리하다.
- P7에 Google Search Console / Naver 서치어드바이저 / Bing 등록 작업을 추가한다.

**현실적 기대치** — 새 도메인은 외부 링크가 없어 초기 색인이 느리다. 전체 색인까지 수 주~두세 달이 걸리는 것이 정상이며, 이를 결함으로 보지 않는다.

## D-10. 메인 디자인 컨셉 — 성운 속의 신경망

**결정** — 메인 3D 그래프의 배경 세계관을 **우주·성운**으로 잡는다. 심우주의 어둠에 성운이 퍼져 있고 노트가 별처럼 떠 있으며, 위키링크가 별자리이자 시냅스 역할을 한다.

**근거** — 고객이 "우주 느낌, 성운"을 요청했다. 기존의 뉴런 비유와 충돌하지 않는다. 은하 필라멘트 구조와 신경망 구조는 시각적으로 닮아 있어, 멀리서는 성운·가까이서는 발화하는 뉴런으로 자연스럽게 이어진다.

**구현 방침** — 성운은 텍스처 이미지가 아니라 GLSL 프래그먼트 셰이더의 FBM 노이즈로 생성한다. 용량 부담이 없고 해상도에 무관하며 무한히 부드럽게 흐른다.

**절제 원칙** — 성운·bloom·파티클은 과하면 즉시 싸구려로 보인다. 배경 색은 2~3색으로 제한, 성운은 항상 노드보다 어둡게, 궤도 1회전 90초 이상, bloom은 가독성을 해치지 않는 선에서 정지. 기획 문서 §7 참조.

## D-11. 정식 주소는 `www.hskim.me`

**결정** — 사이트의 정식(canonical) 주소를 `https://www.hskim.me` 로 한다. `hskim.me`(apex)는 zone hold 가 해제되는 시점에 리다이렉트로 붙인다.

**경위** — `hskim.me` 를 Cloudflare 에 추가하려 할 때 **zone hold** 에 막혔다. zone hold 는 Enterprise 전용 기능이고 Enterprise zone 에 기본 적용되므로, 사업자 계정(hosting.kr 추정)이 이 도메인의 zone 을 보유하고 있다는 뜻이다. 우회 경로를 전부 시도했다.

| 시도 | 결과 |
|---|---|
| 네임서버를 Cloudflare 로 이전 | ❌ zone hold |
| Pages 커스텀 도메인 + 외부 DNS (`www`) | ✅ **동작** |
| Pages 커스텀 도메인 + 외부 DNS (apex) | ❌ Pages 가 apex 는 외부 DNS 를 지원하지 않음 |
| hosting.kr URL 포워딩 | ❌ `@` 의 모든 레코드 삭제를 요구 — MX 포함이라 메일이 끊긴다 |
| 다른 등록기관으로 이전 | ❌ Pages 의 apex 제약은 그대로 |

**근거** — `www` 를 정식 주소로 쓰는 것은 흔한 구성이고 SEO 상 불이익이 없다. canonical URL 과 `sitemap.xml` 을 `www` 로 통일하면 된다(D-09). apex 는 나중에 301 로 합류시키면 평가도 이전된다.

**부수 효과** — 네임서버를 Cloudflare 로 옮기지 않았으므로 **Google Workspace 메일에 리스크가 전혀 없다.** 결과적으로 원래 계획보다 안전한 구성이 됐다.

**잃은 것** — Cloudflare Access 를 쓸 수 없다. 공개 전 잠금(P7 이전)은 다른 방법으로 구현해야 한다 → Pages Functions 기반 접근 제어 또는 robots·noindex 유지.

**해제 시 할 일** — zone hold 가 풀리면 네임서버를 Cloudflare 로 옮기고, apex 를 Pages 에 추가한 뒤 `hskim.me → www.hskim.me` 301 을 건다. 이때 MX·TXT 를 먼저 Cloudflare 에 옮겨 두는 절차(infra/README.md 4단계)를 그대로 따른다.
