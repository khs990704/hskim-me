## 1. 무엇을 만드는가

Obsidian Vault에 쌓인 지식 노트·프로젝트 케이스·포트폴리오를 **원본 구조와 내용 그대로** 공개하는 개인 웹사이트.

세 가지를 겸한다.

- **테크 블로그** — `01 Knowledge DB`의 지식 노트 431개
- **포트폴리오** — `02 Project Cases`의 프로젝트 케이스 121개와 `03 Portfolio/Portfolio.md`
- **자기소개** — 위 둘을 엮어 "이 사람이 무엇을 알고 무엇을 만들었는가"를 보여주는 화면

여기에 더해, **외부 검색 엔진에서 노트의 키워드로 검색했을 때 해당 노트가 결과에 노출되어야 한다.** 이건 마감 단계의 장식이 아니라 라우팅·렌더링 방식을 규정하는 설계 제약이다(§9).

기존 블로그 플랫폼과 다른 점은 **글 목록이 아니라 지식의 연결 구조가 첫 화면**이라는 것이다. 노트 사이의 위키링크를 뉴런과 시냅스처럼 3D로 그리고, 방문자는 글 제목 리스트가 아니라 연결망을 훑으며 관심 가는 노드로 들어간다.

### 왜 이렇게 만드는가

김희섭 님의 Vault는 이미 잘 구조화된 지식 그래프다. 노트마다 `## 관련 개념` 섹션에 위키링크가 달려 있고, MOC(Map of Content) 문서가 분류 축을 잡아 준다. 일반적인 블로그 형태로 펼치면 이 구조가 전부 평평해지면서 사라진다. **연결 구조 자체가 이 사람의 사고 방식을 보여주는 자산**이므로, 그걸 그대로 보여주는 게 이 사이트의 핵심 가치다.

채용 담당자용으로 정리된 이력은 **별도 PDF**로 제공한다. 따라서 이 웹사이트는 "읽기 쉬운 이력서" 역할을 겸할 필요가 없고, 탐색 경험 자체에 집중할 수 있다.

### 이번 범위가 아닌 것 (비목표)

- 댓글, 방문자 계정, 뉴스레터 구독
- CMS·관리자 화면 — 글쓰기는 Obsidian에서만 한다
- 영어판 본문 (D-05: 구조만 열어 두고 구현은 이후)
- AI 검색 (요구사항 8번, P8에서 별도 착수)

### 마크다운 형식 특성 (파이프라인 요구사항의 출처)

Vault를 실제로 조사해 확인한 사실이다.

- **YAML frontmatter가 없다.** 노트는 `# 제목` H1으로 시작한다 → 제목·날짜·태그를 파일 경로와 H1에서 추론해야 한다.
- **위키링크가 두 형태로 섞여 있다.** `[[React]]` 같은 짧은 형태와 `[[02 Project Cases/Project Index/04 Personal/Personal Projects]]` 같은 전체 경로 형태 → 링크 해석기가 둘 다 처리해야 한다.
- **파일명에 한글·공백·`&`가 들어간다** (`Idea Mining & Specification Validation Harness.md`, `포트폴리오 작성 규칙.md`) → URL 슬러그 생성 규칙이 필요하다.
- **수식**을 인라인 `$...$`, 블록 `$$...$$`로 쓴다 → KaTeX 렌더링 필요.
- **표**를 적극 사용한다 → 좁은 화면에서 가로 스크롤 처리 필요.
- **MOC 문서**가 분류 허브 역할을 한다 → 그래프에서 허브 노드로 시각적 강조 대상.
- **`Portfolio.md`가 187KB 단일 파일**이다 → 그대로 한 페이지에 던지면 로딩·탐색이 모두 나쁘다. 빌드 시 `##` 섹션 단위로 분할하고 목차·앵커를 생성한다.

## 4. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 콘텐츠 변환 | **Quartz v4** (파서·링크 해석·그래프 데이터만) | Obsidian 문법(위키링크, 별칭, 임베드, 콜아웃, 수식, 백링크)이 이미 검증된 상태로 구현돼 있다. 직접 만들면 초기 비용이 크다 → D-02 |
| 변환 산출물 | JSON (`content/*.json`, `graph.json`, `search-index.json`) | 프론트엔드를 Quartz 구조에서 완전히 분리하는 경계면. 나중에 Quartz를 걷어내도 이 스키마만 지키면 프론트는 그대로 |
| 프론트엔드 | **Next.js 15 App Router / 정적 export** | 모든 노트를 정적 HTML로 뽑아 SEO·공유·초기 로딩을 확보. 추후 AI 검색 UI를 React로 붙이기 좋다 |
| 3D 그래프 | **three.js + react-three-fiber**, 레이아웃은 **d3-force-3d** | 뉴런 발광·시냅스 신호 같은 커스텀 셰이더 표현이 필요하다. 1단계는 `react-force-graph-3d`로 빠르게 검증하고, 비주얼 요구를 못 채우면 R3F 직접 구현으로 전환 |
| 성운 배경 | **GLSL 프래그먼트 셰이더** (FBM 노이즈) | 텍스처 이미지 없이 무한히 부드럽게 흐르는 성운을 만든다. 용량 부담 0, 해상도 무관 |
| 스타일 | **Tailwind CSS** + CSS 변수 테마 | 김희섭 님 Knowledge DB에 이미 노트가 있는 익숙한 스택 |
| 애니메이션 | **Framer Motion** (2D UI), R3F 자체 루프 (3D) | 상동 |
| 수식 | **KaTeX** | Vault가 `$...$` / `$$...$$`를 쓴다. 해당 문서 30개에서만 로드 |
| 다이어그램 | **Mermaid** | Vault에 flowchart가 있고, 운영 규칙상 프로젝트 구조도가 추가될 예정 |
| 코드 하이라이트 | **Shiki** (빌드 타임) | 런타임 JS 0KB, 정적 출력과 궁합이 좋다 |
| 검색 | **FlexSearch** (클라이언트, 사전 생성 인덱스) | 550여 문서 규모면 서버 없이 충분하다. P8의 AI 검색과 역할이 다름(키워드 vs 의미) |
| 폰트 | 본문 **Pretendard**, 코드 **JetBrains Mono** | 한글 본문 가독성 |
| 메타데이터·SEO | **next/metadata** + 빌드 타임 JSON-LD·사이트맵 생성 | 노트에 frontmatter가 없어 요약·제목을 본문에서 추출해 주입해야 한다 (§9) |
| OG 이미지 | **Satori** (빌드 타임 SVG→PNG) | 노트별 OG 이미지를 런타임 없이 정적 생성 |
| 호스팅 | **Cloudflare Pages** + Cloudflare DNS | D-04 |
| CI | **GitHub Actions** | D-03 |

## 5. 콘텐츠 파이프라인 명세

### 처리 순서

```
Vault 사본
  → ① 화이트리스트 필터   공개 폴더만 통과 (D-01)
  → ② 제외 규칙 적용      publish:false / exclude.txt / _접두사 (D-06)
  → ③ 콘텐츠 가드         금칙 패턴 검출 시 빌드 중단
  → ④ Quartz 변환         마크다운 → HTML, 위키링크 해석, 백링크 수집
  → ⑤ 커스텀 emitter      JSON 출력
  → ⑥ 후처리              Portfolio.md 섹션 분할, 그래프 초기 좌표 사전 계산,
                         검색 인덱스 생성
```

### 출력 스키마 (프론트엔드와의 계약)

`content/<slug>.json` — 노트 1개

```jsonc
{
  "slug": "knowledge/software-engineering/frontend/react",
  "title": "React",
  "source": "01 Knowledge DB/02 Software Engineering/02 Frontend/React.md",
  "kind": "note",          // note | project | portfolio | moc | about
  "category": ["01 Knowledge DB", "02 Software Engineering", "02 Frontend"],
  "html": "<h2>핵심 맥락</h2>...",
  "description": "React는 컴포넌트 단위로 UI를 구성하는 JavaScript 라이브러리다.",  // 본문 첫 문단에서 추출, meta description 용
  "toc": [{ "depth": 2, "text": "핵심 맥락", "id": "핵심-맥락" }],
  "features": { "math": false, "mermaid": false, "code": true, "table": true, "image": false },  // 무거운 라이브러리 조건부 로딩용
  "links":     [{ "slug": "...", "title": "..." }],   // 이 노트가 거는 링크
  "backlinks": [{ "slug": "...", "title": "..." }],   // 이 노트를 가리키는 링크
  "tags": [],
  "updatedAt": "2026-09-18T09:00:00Z",   // Vault git 커밋 시각
  "locale": "ko"                          // D-05: 영어 확장 대비
}
```

`graph.json` — 그래프 전체

```jsonc
{
  "nodes": [{
    "id": "knowledge/.../react",
    "title": "React",
    "kind": "note",
    "group": "software-engineering",  // 색상 그룹
    "degree": 12,                     // 연결 수 → 노드 크기
    "pos": [12.4, -3.1, 8.9]          // 빌드 시 사전 계산한 초기 좌표
  }],
  "links": [{ "source": "...", "target": "...", "weight": 1 }]
}
```

**초기 좌표를 빌드 시점에 계산해 두는 이유** — 브라우저에서 550개 노드의 force 시뮬레이션을 처음부터 돌리면 첫 몇 초가 노드들이 튀어나오며 자리를 잡는 시간이 된다. 좌표를 미리 계산해 넣으면 첫 프레임부터 완성된 형태로 보이고, 새로고침해도 배치가 같아서 "그 위치에 있던 노드"를 다시 찾을 수 있다.

### 슬러그 규칙

한글 파일명을 URL에 어떻게 넣느냐는 되돌리기 비싼 결정이다(링크 공유·SEO에 영향).

- 한글 제목은 **한글 그대로 유지하고 URL 인코딩**한다. `/notes/지식화-DB-운영` 형태.
  로마자 변환(`jisikhwa-db`)은 읽을 수 없고, 영문 번역은 유지보수가 붙는다.
- 공백 → `-`, `&` 등 특수문자는 제거, 대소문자는 소문자로.
- **슬러그 ↔ 원본 경로 매핑을 `slug-map.json`으로 저장**한다. 노트 이름이 바뀌어도 기존 URL에서 리다이렉트할 수 있게 하기 위함이다.

### 노트 페이지 레이아웃

```
┌────────────┬──────────────────────────────┬──────────────┐

```

- 사이드 트리는 Vault의 폴더 계층을 그대로 반영한다 (요구사항 5·6번).
- 오른쪽 **미니 그래프**는 전역 그래프의 부분집합이다. 메인 그래프로 돌아가지 않고도 주변 맥락을 탐색할 수 있게 한다.
- 좁은 화면에서는 두 사이드가 접히고 본문만 남는다.

## 7. 디자인 방향

### 전체 컨셉 — 성운 속의 신경망

메인의 세계관은 **우주**다. 심우주의 어둠 속에 성운이 퍼져 있고, 그 안에 지식 노트가 별처럼 떠 있다. 노트를 잇는 위키링크는 별자리이자 동시에 뉴런의 시냅스다. 방문자는 이 성운을 유영하며 관심 가는 별로 들어간다.

"우주"와 "뉴런"은 서로 다른 비유가 아니다. 둘 다 **점들이 연결로 구조를 이루는 그림**이고, 실제로 은하 필라멘트 구조와 신경망 구조는 시각적으로 매우 닮아 있다. 이 사이트는 그 겹침을 그대로 쓴다 — 멀리서 보면 성운, 가까이 가면 발화하는 뉴런.

| 요소 | 방향 |
|---|---|
| 배경 | 심우주 검정 `#03040A` 기반. 화면 전체에 느리게 흐르는 성운(nebula) — 짙은 남보라·청록이 번지는 볼류메트릭 안개 |
| 성운 구현 | 프래그먼트 셰이더의 FBM(fractal Brownian motion) 노이즈로 생성. 텍스처 이미지를 쓰지 않아 용량 부담이 없고 무한히 부드럽게 흐른다 |
| 별먼지 | 수천 개의 미세 파티클이 깊이감을 만든다. 카메라 이동 시 시차(parallax)로 거리감 표현 |
| 노드 | 발광 구체 + bloom. 크기는 연결 수(degree), 색은 8개 대분류별. 가까이 가면 표면에서 미세한 맥동 |
| 엣지 | 얇은 반투명 발광선. 평상시 희미하고, 호버 시 해당 경로만 밝아진다 |
| 신호 | 엣지를 따라 흐르는 빛 입자 — 뉴런 발화이자 성간 신호. 초당 소수만 발생시켜 산만하지 않게 |
| 카메라 | 진입 시 아주 느린 자동 궤도 회전. 사용자 입력이 들어오면 즉시 중단 |
| 호버 | 노드 확대 + 제목 라벨 + 1-hop 이웃만 강조, 나머지는 어둡게 |
| 클릭 | 카메라가 노드로 접근 → 노트 페이지로 전환. 성운 속으로 들어가 별에 착륙하는 느낌의 연속 동작 |

**절제 원칙** — 성운·bloom·파티클은 과하면 즉시 싸구려로 보인다. 다음을 지킨다.
- 색은 배경 계열 2~3색으로 제한하고, 채도 높은 색은 노드에만 쓴다
- 성운은 항상 노드보다 어둡다. 배경이 주인공이 되면 안 된다
- 움직임은 "느리다"고 느낄 정도로 늦춘다. 궤도 1회전 90초 이상
- bloom 강도는 글자 가독성을 해치지 않는 선에서 멈춘다

## 8. 자동 반영 (요구사항 7번)

```
Obsidian에서 노트 작성
   → Obsidian Git 플러그인이 커밋·푸시 (수동 또는 N분 주기)
   → hskim-vault push 감지
   → hskim-me 빌드 트리거
   → 필터 → 가드 → 변환 → 빌드 → Cloudflare Pages 배포
   → 수 분 내 hskim.me 반영
```

**커밋 = 게시 의사 표시**로 취급한다(D-03). 작성 중인 초안이 자동으로 올라가지 않는 최소한의 안전장치다. 초안을 커밋해야 하는 경우엔 `publish: false`를 쓴다.

**삭제·이름 변경 대응** — 노트가 사라지면 해당 URL은 404가 된다. `slug-map.json`의 이전 이력을 이용해 이름 변경은 301 리다이렉트로 처리한다. §9에서 설명하듯 URL 안정성은 검색 노출에 직결되므로, 이 처리는 선택이 아니라 필수다.

## 9. 검색 노출 설계 (요구사항 추가분)

**목표** — 방문자가 Google·Naver에서 `Framer Motion 사용 맥락`, `LakeFS MinIO 연동` 같은 키워드를 검색했을 때, Vault 노트가 검색 결과에 뜨고 그 노트 페이지로 바로 들어온다.

이건 마감 단계에 붙이는 장식이 아니라 **설계 제약**이다. 뒤에 얹으려면 라우팅과 렌더링 방식을 다시 손대야 하므로, 처음부터 구조에 넣는다.

### 이 사이트 특유의 문제 — 메인에 텍스트가 없다

`/`가 3D 그래프라서, 홈페이지 HTML에는 검색 엔진이 읽을 본문이 사실상 없다. 크롤러는 보통 홈에서 출발해 링크를 타고 내부 문서를 발견하는데, 그 경로가 끊긴다. 대응은 세 겹이다.

1. **모든 노트 페이지를 정적 HTML로 생성한다.** 본문·제목·소제목이 HTML 안에 그대로 들어간다. 그래프는 입구일 뿐, 검색 대상은 노트 페이지다 → [[Static Site Generation]]
2. **`/index-all` 텍스트 인덱스를 크롤러의 출발점으로 삼는다.** 전체 노트를 폴더 계층 그대로 나열한 정적 페이지다. 홈의 `<noscript>`와 푸터에서 여기로 링크한다.
3. **`sitemap.xml`에 전 URL을 싣고** Search Console에 제출한다. 홈에서 링크를 못 타더라도 색인 경로가 확보된다.

### 페이지별 메타데이터 (파이프라인이 자동 생성)

노트에 frontmatter가 없으므로 전부 본문에서 뽑아낸다.

| 항목 | 생성 방식 |
|---|---|
| `<title>` | `노트 제목 · 분류 – hskim.me` |
| `description` | 본문 첫 문단에서 120~160자 추출 (Vault 노트는 대부분 첫 문단이 정의문이라 요약으로 적합) |
| `<h1>` | 노트 H1 그대로. 페이지당 정확히 하나 |
| 소제목 | `## 핵심 맥락`, `## 사용 맥락` 등을 `<h2>`로 유지 — 키워드가 구조적 위치에 놓인다 |
| canonical | 절대 URL 1개 고정 |
| OG / Twitter Card | 제목·요약 + 노드 주변 그래프를 렌더한 페이지별 OG 이미지 |
| JSON-LD | `TechArticle` 스키마. 제목, 요약, 수정일, 저자, 분류 |
| `lang` | `ko` (D-05) |

### URL 전략

- **한글 슬러그를 유지한다.** `/notes/지식화-db-운영` 형태. 검색 엔진은 URL의 퍼센트 인코딩을 디코딩해 처리하며, 한글 키워드가 URL에 들어가면 오히려 매칭에 유리하다. 로마자 변환은 검색어와 일치하지 않아 손해다.
- **URL을 함부로 바꾸지 않는다.** 색인이 쌓인 URL이 404가 되면 그동안의 노출이 사라진다. 노트 이름 변경 시 `slug-map.json` 이력으로 301 리다이렉트를 반드시 발행한다.
- 슬러그는 소문자·하이픈 정규화만 하고 의미를 보존한다.

### 검색 엔진 등록 (P7)

| 대상 | 작업 |
|---|---|
| Google | Search Console 도메인 소유 확인, `sitemap.xml` 제출, 색인 상태 모니터링 |
| Naver | 서치어드바이저 등록·사이트맵 제출. 한국어 기술 키워드 유입에서 비중이 크다 |
| Bing | Webmaster Tools 등록 (Google Search Console 연동으로 간소화 가능) |
| `robots.txt` | 전체 허용 + 사이트맵 위치 명시 |

### 현실적 기대치

새 도메인은 외부 링크가 없어 초기 색인이 느리다. 전체 노트가 색인되기까지 **수 주에서 두세 달**이 걸리는 게 정상이며, 이건 기술적 결함이 아니다. 할 수 있는 건 색인 경로를 막지 않는 것, 각 페이지가 검색 의도에 맞는 내용을 실제로 담게 하는 것, 그리고 GitHub 프로필·기술 커뮤니티 등에서 도메인을 노출해 초기 유입을 만드는 것이다.

## 10. 공개 전 안전장치

D-01에서 회사 프로젝트 케이스를 포함해 공개하기로 했으나, 자동화된 패턴 검사만으로는 NDA·영업비밀 위험을 감당할 수 없다는 판단에 따라 D-08로 규칙을 강화했다.

### 계층 1 — 회사 케이스는 옵트인 (D-08)

`02 Project Cases/Project Index/03 Company/` 하위는 **기본 비공개**다. 노트 frontmatter에 `publish: true`가 명시된 것만 공개한다. 나머지 폴더는 D-06의 자동 공개 규칙을 그대로 따른다.

**이유** — 가드가 잡을 수 있는 건 내부 도메인, 사설 IP, 사번·계정 형식, 고객사 고유명사처럼 기계적으로 식별되는 것뿐이다. NDA에서 실제 쟁점이 되는 것은 대개 "그 회사가 이 문제를 어떻게 풀었는가"라는 설계 판단 자체이고, 고유명사를 모두 제거해도 내용만으로 식별된다. 정규식은 이를 판단할 수 없다. 더 중요한 건 미래다 — 자동 공개로 두면 앞으로 회사 업무를 지식화할 때마다 커밋 즉시 공개된다.

### 계층 2 — 콘텐츠 가드

`pipeline/guard-rules.txt`에 금칙 패턴을 등록하고, 빌드 중 검출되면 **빌드를 실패시킨다**. 통과시키려면 노트를 수정하거나 명시적으로 예외 등록해야 한다.

| 패턴군 | 예 |
|---|---|
| 내부 네트워크 | 사설 IP 대역, `*.internal`, `*.local`, 사내 도메인 |
| 자격 증명 형태 | API 키·토큰 형태 문자열, `.env` 내용, 커넥션 문자열 |
| 조직 식별자 | 고객사·협력사 고유명사, 사번·계정 형식, 내부 시스템 코드명 |
| 계약·수치 | 계약 금액, 내부 KPI 수치 |

가드는 보조 장치다. **가드 통과가 공개 승인을 뜻하지 않는다.**

### 계층 3 — 검수 체크리스트

`publish: true`를 붙이기 전에 노트별로 확인한다. 체크리스트는 `docs/04-communication/company-case-review.md`에 두고 검수 결과를 기록한다.

1. 회사 고유의 아키텍처 판단·알고리즘·데이터 스키마가 드러나는가
2. 고객사·협력사를 식별할 수 있는가
3. 내부 수치(성능, 규모, 비용)가 들어 있는가
4. 재직 당시 계약·서약의 범위에 저촉되는가
5. 같은 내용을 **"내가 무엇을 할 수 있는가"** 수준으로 일반화해도 포트폴리오 가치가 유지되는가 → 유지된다면 일반화한 버전을 공개한다

5번이 핵심이다. 대부분의 경우 "MLflow·MinIO 기반 MLOps 플랫폼의 백엔드 API와 스토리지 연동을 구현했다"까지는 공개해도 문제가 없고, 포트폴리오로서의 가치도 거의 그대로다. 잃는 것은 구현 세부인데 그건 애초에 공개 대상이 아니다.

### 계층 4 — 비공개 프리뷰

도메인 연결 전까지 Cloudflare Access로 프리뷰 URL을 잠가 두고 작업한다.

최종 공개 판단은 고객이 한다. 시스템은 "놓친 것"을 줄이는 역할만 한다.

## 12. 향후 확장 — AI 검색 (요구사항 8번)

본 범위 밖이지만, 나중에 얹을 때 구조를 뜯어고치지 않도록 지금 설계에 반영해 둔다.

- 파이프라인이 만드는 `content/*.json`이 그대로 임베딩 입력이 된다 (별도 추출 작업 불필요)
