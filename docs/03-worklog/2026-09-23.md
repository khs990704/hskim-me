## 6. 모바일에서 검색을 누르면 화면이 확대된다

iOS Safari 는 **글자가 16px 미만인 입력란에 초점이 가면** 화면을 확대한다. 되돌려 주지도 않는다. 검색 입력란이 14px 이었다.

흔한 처리는 `viewport` 에 `maximum-scale=1` 을 넣는 것인데 쓰지 않았다. 그러면 본문도 두 손가락으로 키울 수 없다. 노트가 표와 코드블록투성이라 확대해서 봐야 할 때가 많고, 시력이 약한 사람에게는 사이트를 못 읽게 만드는 설정이다.

글자를 키워 확대할 이유 자체를 없앴다.

```css
@media (pointer: coarse) {
  input, textarea, select { font-size: 16px; }
}
```

**폭이 아니라 입력 장치로 갈랐다.** 폭으로 가르면 폰을 가로로 눕혔을 때 640px 을 넘어 다시 14px 이 되고 확대가 돌아온다. iPhone 14 Pro Max 는 가로로 932px 이다.

## 7. 검색 순위가 틀렸다

고객이 `데이터 전처리` 로 검색했더니 `데이터` 만 든 impai 가 1위로 나왔다. AND 가 안 걸린 것처럼 보였다.

**AND 는 동작하고 있었다.** 걸린 38개 문서가 전부 두 단어를 갖고 있었다. 문제는 순서였다.

```
점수 = 어디서 맞았나 + (40 − 제목 길이)
                        ↑ 범인
```

짧은 제목 보너스가 본문 일치 점수(10점)보다 3배 이상 컸다. `impai` 는 제목이 5자라 35점을 그냥 받았고, 본문에 각각 한 번씩 스친 것만으로 1위가 됐다. 정작 `Data Preprocessing` 은 제목이 길다는 이유로 16위였다.

### 세 가지 교정
1. **보너스는 제목이 맞았을 때만.** 본문에 스친 문서가 제목이 짧다는 이유로 올라오면 안 된다
2. **본문 일치에 횟수 반영.** 한 번 스친 문서와 그 주제를 다루는 문서는 다르다. 8회까지만 세서 제목 일치를 넘지 못하게 했다
3. **발췌는 검색어가 가장 많이 모인 자리로.** 전에는 첫 단어의 첫 일치만 봤다. 그래서 `데이터` 만 강조된 토막이 나왔고 AND 가 안 걸린 것처럼 보였다

### 발췌가 라벨 줄에서 시작하던 문제
제목이 맞은 문서는 첫 일치가 본문 0번 위치라, 발췌가 제목과 그 밑 `기간: …` 줄에서 시작했다.

**제목이 맞은 문서는 요약을 보여준다.** 찾던 문서가 맞는지는 바로 위의 제목이 이미 말해 주고, 다음으로 궁금한 것은 '이게 무슨 글인가' 다. 구글도 이렇게 한다.

색인에서 라벨 줄을 빼는 방법도 검토했으나 **그러면 `PostgreSQL` 로 프로젝트를 찾을 수 없게 된다.** 관련 기술 줄이 유일한 출처다. 찾기는 되고 보여주기만 비껴가도록, 색인에 "문장이 시작하는 위치"(`o`)를 숫자 하나로 실었다. 문서당 5바이트.

### 붙여 쓴 한글
`데이터전처리` 가 0건이었다. 노트 어디에도 그 두 낱말이 붙어 있지 않기 때문이다.

결과가 0건일 때만 낱말을 둘로 갈라 다시 찾는다. 가능한 모든 자리에서 잘라 보고 가장 많이 맞는 쪽을 쓴다. 형태소 분석 없이 되는 범위다. 평소 검색 속도에는 영향이 없다.

### 곁들여
- 본문 정규화 결과를 문서별로 캐시. 글쇠 하나마다 485개 문서의 본문 1.3MB 를 새로 정규화하고 있었다
- 발췌는 화면에 보여줄 30개만 만든다

## 10. 접근성·아이콘 교정

### favicon 이 없었다
`GET /favicon.ico → 404` 가 콘솔에 찍히고 있었다. `app/icon.svg`(연결된 노드 셋)와 `apple-icon.png` 를 넣었다. 아이콘은 16px 로 줄었을 때 살아남아야 하므로 점 셋과 선 둘만 남겼다. `<link rel="icon">` 이 생기면 브라우저가 `/favicon.ico` 를 찾지 않는다.

### 라이트 테마 대비가 미달이었다
측정이 라이트로 돌아서 드러났다. 평소 다크로 보기 때문에 보이지 않던 문제다.

```
                    전             후
라이트  --fg-dim   4.71  →  #565d6a  6.45
        --fg-faint 2.53  →  #676e7a  5.00
다크    --fg-dim   6.26  →  #9aa5b8  7.61
        --fg-faint 3.27  →  #7f8aa1  5.45
메인 하단          2.69  →  #78839c  5.39
```

**라이트에서 `--fg-dim` 도 같이 내렸다.** faint 만 기준(4.5:1)까지 올리면 기존 dim 과 거의 같은 색이 되어 계층이 무너진다. 둘 다 내려야 '본문 > 흐림 > 더 흐림' 이 남는다.

코드블록 배경도 `--bg-soft` → `--surface` 로 바꿨다. bg-soft 위에서는 github-light 키워드 색(`#D73A49`)이 4.15:1 로 미달이었고, 흰 배경에서는 4.57:1 이다.

### 보이는 글자와 접근 이름이 달랐다
검색 단추가 `aria-label="검색"` 인데 보이는 글자는 `검색 Ctrl K` 였다. 음성으로 '검색 Ctrl K' 라고 말해도 이름과 맞지 않아 조작이 실패한다. `aria-label` 을 떼고 `sr-only` 로 바꿨다.

### 닫힌 패널이 탭을 먹고 있었다
검색 패널과 서랍은 닫혀도 DOM 에 남는다(애니메이션 때문). `aria-hidden` 만으로는 안의 단추가 탭 순서에 남아, 탭을 누르면 초점이 보이지 않는 곳으로 사라진다. `inert` 로 바꿨다. 서랍은 링크가 477개라 영향이 컸다.

## 11. 폰트를 우리 쪽으로

CLS 0.139 의 원인은 코드블록이 아니라 **본문 폰트**였다. 한 페이지가 jsdelivr 에 27번 요청했고, 폰트 25개가 제각기 도착할 때마다 본문이 밀렸다.

**렌더 차단 300ms 는 크기가 아니라 연결 비용이다.** CSS 540KB 는 압축되면 21KB 다. 남의 서버에 DNS·TLS·왕복을 하는 시간이 300ms 였고, 압축으로는 줄지 않는다.

### 변수 폰트 + 자체 호스팅
```
                 전        후
CSS            540KB     49KB
페이지당 요청    25건      14건
외부 CDN        27건       0건
CLS            0.139     0.012
LCP             0.8s      0.4s
```

Pretendard Variable 은 굵기 하나로 45~920 을 낸다. Regular·Medium·SemiBold·Bold 를 따로 받을 이유가 없어져 요청이 절반이 됐다.

### preload 는 세어서 정했다
우리 글 전체의 글자를 서브셋별로 세었다.

```
subset 91  521,952자  69.4%   ← 하나가 69%
       90  125,586자  86.1%
       89   47,590자  92.4%
       88   28,174자  96.1%
```

한글 서브셋은 쓰임이 한쪽으로 몰려 있다. 넷만 미리 당기면 96%가 첫 화면에 준비된다. CLS 가 0.012 까지 떨어진 것이 이 덕이다.

### 경로에 판 번호를 넣었다
`/fonts/pretendard-1.3.9/…`. 폰트를 1년 `immutable` 로 캐시하려면(`public/_headers`) 내용이 바뀔 때 주소가 바뀌어야 한다. 판을 올리면 경로가 바뀌므로 예전 폰트를 계속 쓰는 일이 없다.

`scripts/fetch-fonts.mjs` 는 **빌드에 붙이지 않았다.** 빌드가 남의 서버에 기대면 그쪽이 흔들릴 때 배포가 멈춘다. 판을 올릴 때만 손으로 돌리고 파일은 저장소에 둔다.

### 측정을 한 번 잘못 읽었다
처음엔 FCP 0.5→0.7, LCP 0.8→1.2 로 **나빠진 것처럼 나왔다.** 원인은 테스트 서버였다. `python -m http.server` 는 HTTP/1.0 이라 폰트 14개를 매번 새 연결로 받는다. keep-alive 와 압축을 하는 서버로 바꿔 재니 0.4s 였다. 로컬 측정값을 그대로 믿으면 안 된다는 사례.
