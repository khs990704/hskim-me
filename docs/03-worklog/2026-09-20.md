### 4. 고객 검수 및 반영 (1차 승인)
- 기획 문서·개발 계획 **승인 완료**

  - D-08: `03 Company/` 하위를 **기본 비공개 + `publish: true` 옵트인**으로 전환 (D-01 일부 대체)
  - 근거: 가드는 고유명사·IP·자격증명만 잡음. 실제 쟁점인 "설계 판단 자체"는 정규식으로 판별 불가. 더 중요한 건 향후 회사 업무 지식화 시 커밋 즉시 공개되는 경로
  - 4계층 방어 정리 — 옵트인 / 콘텐츠 가드 / 5항목 검수 체크리스트 / 비공개 프리뷰
  - 공개 불가 케이스는 삭제 대신 **일반화 버전** 작성 우선 검토
- **요구사항 추가: 외부 검색 엔진 키워드 노출** (D-09)
  - 기획 문서 §9 신설 — 메인이 3D 그래프라 홈에 크롤러가 읽을 본문이 없는 구조적 문제와 3중 대응(정적 HTML / `/index-all` 진입점 / sitemap)
  - frontmatter가 없어 `description`을 본문 첫 문단에서 자동 추출해야 함 → **P1 스키마에 필드 추가**
  - 한글 슬러그 유지(로마자 변환 안 함), URL 안정성·301 리다이렉트를 필수로 격상
  - P7에 Google Search Console / Naver 서치어드바이저 / Bing 등록 추가
- **디자인 방향 확정: 우주·성운** (D-10)
  - GLSL FBM 노이즈 셰이더로 성운 생성 (텍스처 미사용), 별먼지 파티클, 시차

### 5. 회사 케이스 검수 체계 확정 (고객 위임)
- 고객이 "첫 회사라 누출 없이 공개하는 방법을 잘 모른다"며 판단을 위임 → D-08 확정
- [company-case-review.md](../04-communication/company-case-review.md) 전면 재작성
  - **판별 기준** — "회사 밖 사람이 알려면 회사 안에 있어야 했는가"를 단일 판별 질문으로 정리. 기술 스택 / 역할 / 결과 / 아키텍처 / 고객·제품 / 보안 도메인 6개 축의 안전-위험 대조표 작성
  - **재작성 5공식** — 주어를 나로 / 고유명사를 범주로 / 수치를 정성 표현으로 / 판단 근거 제거 후 결과만 / 구조도는 담당 범위까지
  - 보안 제품 내부 동작은 공격 표면 정보가 되므로 한 단계 보수적으로 적용
  - 원본 노트는 수정하지 않고 **공개용 별도 노트로 분리**
- 역할 분담 — 제작자가 판정 초안·재작성안 작성, 고객은 계약·서약 판단과 최종 승인
- **1차 판정을 P7 → P1으로 앞당김.** 파싱이 도는 단계라 추가 비용이 없고, 공개 가능 규모를 알아야 P5 포트폴리오 구성을 짤 수 있음
